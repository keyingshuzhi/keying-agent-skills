# Dependency Auditor · 执行指南

## 适用性判别

**触发：**
- 审计 Python / npm 项目依赖是否存在风险。
- 检查 lockfile 与实际安装版本是否一致。
- 评估升级某个依赖的兼容性影响。
- 梳理项目许可证与依赖供应链风险。

**不触发：**
- 不涉及依赖的代码安全审查 → code-reviewer。
- 正在诊断具体报错且原因不明 → bug-investigator。
- 直接要求安装/升级全部依赖 → 需要明确变更授权与实施计划。
- 只询问某个项目的技术栈 → project-analyst。

## 逐步执行检查表

### Step 1 — 确认审计边界

- 目标：确定生态系统、工作区、环境、直接与间接依赖范围，以及用户关注的安全/兼容/许可风险。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 2 — 盘点可重复证据

- 目标：读取 manifests、lockfiles、SBOM、依赖树、运行时与系统架构；识别单一项目、多工作区和条件依赖。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 3 — 核对解析结果

- 目标：对比声明约束、锁定版本和实际安装；未能访问安装环境时仅报告锁文件所示版本，不冒充运行时事实。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 4 — 查证外部风险

- 目标：若可访问可信公告/数据库，记录漏洞 ID、影响版本范围、修复版本、查询时间、来源及适用条件；离线时仅报告未核验风险，不能断言最新 CVE 状态。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 5 — 评估影响

- 目标：结合实际使用、可达性、运行时平台、传递路径及许可证条件分类；CVSS 不等于项目实际风险。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 6 — 制定处置建议

- 目标：按必要性、兼容性与迁移成本建议最小版本升级、隔离、替换或保持现状；不自动执行升级。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 7 — 生成审计报告

- 目标：包含范围、时间点、证据、严重度、可信度、建议和遗漏范围；不得声称完成全面供应链审计。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

## 风险控制清单

- [ ] 默认只读，不运行可能隐含安装、升级或修改锁文件的命令。
- [ ] 不得自动下载或执行来源不明的安装脚本。
- [ ] 避免输出 .npmrc、pip 配置及私有源中的凭据；仅报告脱敏信息。
- [ ] 没有实时漏洞数据库或官方公告时必须写明“未验证最新漏洞状态”。
- [ ] 许可证相容性需视发布方式、依赖类型和具体条款判断，不替代专业法律意见。
- [ ] 依赖可疑不意味着恶意；避免无证据的恶意软件断言。

## 证据和报告

```text
审计范围/生态/时间：
证据来源（manifest/lockfile/installed/SBOM/公告）：
依赖清单与解析状态：
发现项（包、版本/范围、路径、风险、证据、置信度）：
安全公告核验状态与查询时间：
兼容性/许可证影响：
优先处置建议及回滚：
未覆盖范围和剩余风险：
```

## 交接规范

交接时仅包含当前问题的范围、已确认事实、未知条件、可复现步骤或验证计划；不要把无证据猜测写成确定结论。
