# Test Engineer · 执行指南

## 适用性判别

**触发：**
- 给这个模块设计单元测试 / 集成测试。
- 评估这个 PR 的回归测试范围。
- 在安全环境中运行已有测试并分析失败。
- 为这次修复制定验收测试。

**不触发：**
- 仅需要对代码做静态审查 → code-reviewer。
- 主要任务是定位未知故障根因 → bug-investigator。
- 用户要求直接实现业务功能 → 实现类能力。
- 仅查询 GitHub Actions 状态 → gh-cli。

## 逐步执行检查表

### Step 1 — 定义测试契约

- 目标：确定被测对象、预期行为、可观察输出、成功判据及非目标；缺少需求时从代码与文档提取候选预期并标注待确认。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 2 — 发现测试环境

- 目标：识别语言、框架、测试目录、manifest/lockfile、现有命令、fixture、mock、依赖服务及CI配置；不臆造运行条件。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 3 — 设计测试矩阵

- 目标：按风险选择单元/集成/契约/E2E/回归；包含正常、边界、异常、状态转换与权限场景，显式区分输入、预期、依据。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 4 — 制定执行计划

- 目标：先检查工具权限、测试写入范围、数据隔离、外部请求、密钥与清理方案；无法隔离或可能影响生产时仅提供计划。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 5 — 安全执行（条件允许）

- 目标：优先运行最小相关测试集，再按需要扩大；记录原始命令、工作目录、环境、退出码、测试报告位置与关键输出。用户要求只分析时不得执行有写入的测试。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 6 — 解释结果

- 目标：按用例标记 PASS/FAIL/BLOCKED/SKIPPED/NOT RUN；区分产品缺陷、测试缺陷、环境失败和不稳定测试；不能把断言失败直接定性为产品 Bug。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

### Step 7 — 报告与移交

- 目标：记录覆盖目标、证据、失败复现方式、未执行项和剩余风险；仅在证据足够时向 bug-investigator 移交具体故障。
- 记录当前输入证据、决策与未验证项。
- 仅在本步骤实际完成后才标记完成。

## 风险控制清单

- [ ] 禁止自动使用生产数据库、真实支付、真实邮件或第三方写接口做测试。
- [ ] 不安装新依赖、不更新快照、不修改源码、不改变环境配置，除非用户授权且风险可控。
- [ ] 所有 PASS 必须有真实可追溯的执行证据；测试代码生成完成仅等于 DRAFT/NOT RUN。
- [ ] 覆盖率数字必须来自明确工具输出并说明范围；不得用测试数量代替覆盖率。
- [ ] 测试设计可只读；测试执行可能写缓存、快照或数据库，先识别副作用。

## 交接规范

交接时仅包含当前问题的范围、已确认事实、未知条件、可复现步骤或验证计划；不要把无证据猜测写成确定结论。
