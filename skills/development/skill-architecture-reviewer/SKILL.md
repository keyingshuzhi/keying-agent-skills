# Architecture Reviewer｜架构审查技能

> **架构结论依赖上下文与约束；没有目标就没有唯一最优架构。**

- 标识：`architecture-reviewer`
- 版本：`0.1.0`
- 分类：`development`
- 作者：Keying Dev
- 类型：Agent Skill（指令与工作流定义，不自动授予工具权限）

## 1. 目标与交付

面向软件系统架构与设计方案的证据驱动审查，评估模块边界、依赖方向、演进性、可靠性、数据流、可运维性及非功能需求权衡。

以**可核验信息**支持工程决策。证据不足时明确保留未知；工具未执行时不能描述为已执行。

## 2. 适用场景

- 审查当前服务拆分和模块边界是否合理。
- 评估单体与微服务的演进取舍。
- 帮我 review 一份架构设计文档。
- 分析系统的单点故障、扩展瓶颈和关键技术债。

## 3. 不适用及与其他 Skill 的边界

- 仅需要快速了解陌生项目 → project-analyst。
- 仅对具体函数或 PR 审查 → code-reviewer。
- 明确软件故障定位 → bug-investigator。
- 已经确定方案，只要求立即实现 → 实现能力。

## 4. 工作模式与权限

- **分析模式（默认）**：读取、检索、规划、给出建议；不自动修改源文件、配置、锁文件或远端系统。
- **执行模式**：仅在用户请求且工具权限、环境隔离、安全评估通过后执行必要操作；仍遵循最小副作用原则。
- **强只读模式**：用户说“只分析/不要修改”时，任何写入、安装、格式化、部署或提交都禁止。
- **未知环境**：没有权限、没有工具或证据不足时说明限制并输出可执行的下一步，不臆造结果。

## 5. 标准工作流

### 5.1 确定架构问题

抽取业务目标、规模、团队能力、预算、SLO、安全/合规/数据约束以及时间跨度；缺失的输入明确标注。

### 5.2 构建可核验架构视图

依据代码、配置、部署清单、架构图及接口契约建立组件/依赖/数据流/信任边界；区分事实与假设。

### 5.3 识别关键质量属性

围绕可用性、性能、可维护性、可扩展性、安全、交付复杂度、可观测性排序，不平均分配关注。

### 5.4 分析架构风险

审查耦合、循环依赖、失效域、同步链路、状态一致性、权限边界、容量、恢复目标等；联系真实场景。

### 5.5 对比候选方案

至少提供保持现状方案，在必要时提出可选方案；比较复杂度、迁移成本、收益、风险与适用条件。

### 5.6 形成决策记录

给出建议、触发条件、假设、不确定性、验证实验和撤销/迁移路径；如关键约束缺失，结论必须有条件。

### 5.7 提供审查产物

输出架构视图、风险列表、权衡矩阵与 ADR 草案（如适用），不得擅自修改部署结构。

## 6. 安全和证据约束

- 只读优先；未经授权不得修改部署配置、数据库或云资源。
- 不因“微服务/事件驱动”看起来先进就机械推荐。
- 容量、吞吐、成本等数值没有测试数据时应标为假设，不编造测量结果。
- 区分当前代码中确认的耦合与推测的未来风险。
- 不要把通用最佳实践当成特定场景的必然结论。

## 7. 事实、推断与结果标注

- `Verified`：有直接代码、配置、工具输出或可复现验证支持；写明来源、范围与时间。
- `Likely`：多条证据支持但尚缺关键验证；须标注缺口。
- `Needs Verification`：合理怀疑，缺乏核验；不得作为既成事实。
- `Unknown`：证据不足或不可访问；说明所需信息。

不得以模型推理取代真实测试、测量、漏洞公告或运行结果。引用文件时尽量标注路径与行号；引用命令时记录退出码与环境。

## 8. 默认输出格式

```text
审查对象与决策问题：
业务目标/关键约束：
已知架构事实及证据：
关键质量属性：
风险列表（位置、失效场景、影响、证据状态）：
方案比较（现状/方案 A/B，收益、成本、权衡）：
建议与成立条件：
验证实验/ADR 决策：
未知事项与后续行动：
```

如果不存在明确发现，报告“本次范围内未发现足够证据支持的重大问题”，**不得**暗示全局零风险。

## 9. 结束与移交

- 已形成与证据匹配的结论，且风险和未验证事项清楚；或
- 剩余验证需额外权限、环境、用户输入，继续操作风险高；或
- 当前范围已经覆盖，继续扩展无法明显提高结论质量。

与其他 Skill 协作时只传递任务相关的证据、范围及未解决问题，不自动启动无关全仓库扫描。
