# Code Reviewer — Review Guide

本文件是 `SKILL.md` 的扩展方法手册。优先遵守主文件中的任务范围、只读策略和纳入 Finding 的证据标准。

## 快速上手：代码审查实战流程

当拿到一个代码变更时，请按照以下步骤进行：

1. **先看上下文**：阅读 PR 描述、相关 Issue，理解变更目的
2. **看变更是什么**：快速浏览 Diff，了解修改的文件和范围
3. **按风险顺序检查**：正确性 → 安全性 → 可靠性 → 性能 → 可维护性 → 测试
4. **为每个问题建立证据链**：位置 → 触发条件 → 执行路径 → 实际结果 → 验证方法
5. **明确输出**：按严重度排序，再按证据等级排序列出 Findings

## 1. 输入分类

| 输入 | 最小必要上下文 | 常见限制 |
|---|---|---|
| 单文件 | 文件内容、接口契约、关键调用方 | 可能缺少项目约束 |
| 代码片段 | 语言、预期行为、调用前提 | 不得声称审查了整个仓库 |
| Git Diff | base/head、修改行、上下文与测试 | 需区分已有问题与本次新增问题 |
| Pull Request | PR diff、描述、目标分支、相关测试 | CI 通过不代表逻辑完全正确 |
| 数据库迁移 | 迁移顺序、旧数据形态、回滚方式 | 禁止在真实数据上直接验证 |

## 2. 证据优先级与限制

直接且可复现的失败测试、确定的执行路径、类型/契约事实优先；一般规范仅为提示线索。动态测试必须记录执行条件及结果；静态判断必须明说尚未运行。

对于变更审查，尽量核对问题是由此次变更新增还是在旧代码中已经存在。如无法确认，标为历史问题或范围外观察，不以本次回归缺陷提交。

## 3. 高价值检查清单

### 正确性

- 空值、空集合、首末元素、边界比较与 off-by-one。
- 缺省参数、异常时返回值、错误处理中的吞异常。
- 时间区间、时区、精度、单位、排序与分页。
- 前后端 API schema、枚举、字段重命名的兼容性。

### 安全

- 权限检查是否作用于对象本身，而非只判断登录状态。
- 用户输入进入 SQL、Shell、模板、文件路径等危险边界时是否有相应保护。
- 上传/下载路径是否存在遍历与越权访问风险。
- Token、密钥、用户隐私是否进入日志、错误响应或源码仓库。
- 不能只因存在安全敏感 API 就断言可被利用。

### 可靠性

- 并发读写是否需要锁/事务/唯一约束。
- 重试是否可能重复扣款、创建资源或重复发送。
- 资源是否在异常路径释放。
- 外部请求是否有合理超时及失败回退。
- 配置默认值是否造成环境意外差异。

### 性能

- 热路径 O(n²) 与数据规模关联是否成立。
- 循环里的 SQL / 网络调用是否形成 N+1。
- 分页、缓存、批量操作是否导致无界资源占用。
- 无基准测量时仅描述代码级风险，不能声称具体性能退化百分比。

### 测试充分性

- 新分支是否有正向、反向和边界测试。
- 断言是否检验真正行为而非仅检验成功返回。
- 集成边界、数据库回滚、权限矩阵是否存在盲区。
- “未覆盖某行”不能代替实际缺陷证据。

## 4. 避免误报的五步法

1. 读取完整条件分支和上游输入约束。
2. 寻找框架、数据库和调用方已有保护。
3. 明确具体触发条件，必要时构造最小输入。
4. 寻找与假设相反的执行路径。
5. 无法确认时标记为 Needs Verification，或不纳入正式 Findings。

## 5. 最小示例

示例是假设性材料，不代表对真实项目的发现。

```python
def page_count(total, size):
    return (total + size - 1) // size
```

如果调用方允许 `size=0` 且没有其它校验，可能引发除零异常。仅看到该函数还不能直接确认缺陷：必须调查公开接口是否保证 `size>=1`。

示例 Finding：

```markdown
### CR-01 [Medium] 在分页大小为零时未校验输入
- 位置：`src/paging.py:2`
- 证据状态：Probable
- 触发条件：公开接口可将 `size=0` 传入 `page_count`。
- 影响：除零异常导致请求失败。
- 依据：该表达式在 size=0 时分母为零；调用方未发现范围检查（列出检查范围）。
- 建议：在 API 输入边界强制 `size>=1` 并为无效输入返回明确错误。
- 验证建议：添加零值、负值和正常值测试。
```

如果 API 已经使用严格校验拒绝 `size=0`，应撤销该 Finding。

## 6. PR 评论策略

- 评论聚焦变更行，必要时引用周边代码；不重复同一根因。
- 标题直述问题，正文说明真实触发与影响。
- 通过 `gh-cli` 或仓库平台发布评论属于写操作，必须有用户授权。
- 不以 Review 的名义自行修改目标分支或合并 PR。

## 7. 审查结束自检

- 每个 Finding 是否可被定位、理解、验证、处理？
- 是否区分了事实、推测、未知？
- 是否检查反证与既有校验？
- 是否标注未运行测试、不可访问文件、缺少环境等限制？
- 是否存在无根据的危急评级或空泛最佳实践？
- 是否遵守只读和数据安全边界？

## 8. 常见问题与解决方案

### 8.1 如何避免过度审查？
**问题**：审查时发现太多小问题，难以聚焦主要风险。  
**解决方案**：
- 严格按照风险顺序（正确性→安全性→可靠性→性能→可维护性→测试）进行
- 对于可维护性问题（如代码风格），仅在严重影响团队协作时才提报
- 记住：目标是找到“有实际价值的缺陷”，不是完美的代码

### 8.2 如何处理不确定的情况？
**问题**：不确定某段代码是否真的有问题，担心漏报或误报。  
**解决方案**：
- 当缺少关键证据时，使用 “Needs Verification” 证据状态
- 明确说明需要什么信息才能确认（例如：需要看到调用方的参数验证）
- 不要为了完成审查而强行给出结论

### 8.3 如何平衡误报和漏报？
**问题**：担心既漏报真问题，又误报假问题。  
**解决方案**：
- 优先降低漏报风险：宁可标记为 “Needs Verification” 也不要漏报
- 对于有潜在风险但证据不足的问题，明确说明需要什么验证
- 记住：代码审查的目标是风险提示，不是给出最终结论

## 9. 更多实战示例

### 9.1 SQL 注入风险
**代码**：
```java
String query = "SELECT * FROM users WHERE name = '" + userInput + "'";
statement.execute(query);
```

**Finding**：
- **位置**：`src/service/UserService.java:45`
- **严重度**：High
- **证据状态**：Probable
- **触发条件**：用户可控制的输入直接拼接到 SQL 查询中
- **影响**：可能导致 SQL 注入攻击，数据库被恶意查询或修改
- **依据**：用户输入未经过任何转义或参数化处理，直接进入 SQL 语句
- **建议**：使用参数化查询或 ORM 框架的查询方法
- **验证建议**：尝试输入 `' OR '1'='1` 作为 userInput，观察是否能绕过认证

### 9.2 并发修改导致的数据不一致
**代码**：
```java
public void transfer(Account from, Account to, double amount) {
    from.setBalance(from.getBalance() - amount);
    to.setBalance(to.getBalance() + amount);
}
```

**Finding**：
- **位置**：`src/service/BankService.java:23`
- **严重度**：High
- **证据状态**：Needs Verification
- **触发条件**：并发调用 transfer 方法
- **影响**：在多线程环境下可能导致账户余额不匹配
- **依据**：方法中对两个账户的余额修改不是原子操作
- **建议**：添加适当的同步机制（如 synchronized 或使用事务）
- **验证建议**：创建多线程测试，并发调用 transfer 方法，检查最终余额是否正确

## 10. 检查清单速查

### 快速正确性检查
- [ ] 空值/空集合处理
- [ ] 边界条件（首元素、尾元素）
- [ ] 离-by-one 错误
- [ ] 异常处理是否完整

### 快速安全检查
- [ ] 输入验证（大小、类型、格式）
- [ ] 权限检查是否在用户输入之前
- [ ] 敏感信息是否泄露到日志或返回值
- [ ] 文件路径是否防范遍历攻击

### 快速可靠性检查
- [ ] 资源是否在异常路径释放
- [ ] 网络请求是否有超时和重试
- [ ] 并发访问是否需要保护
- [ ] 配置更改是否生效需要重启
